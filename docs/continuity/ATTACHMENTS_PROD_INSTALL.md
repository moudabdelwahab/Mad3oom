## Decisions this implements (recommendations from proposal §15.6, awaiting confirmation)
| # | Decision | Implemented as |
|---|---|---|
| S1 | Allowed formats | **Images:** PNG, JPEG, WebP, GIF, 3 MiB. **Video:** MP4, WebM, MOV, 16 MiB. **Audio:** WebM, Ogg, MP3, M4A, WAV, 8 MiB. 1 MiB = 1,048,576 bytes. No SVG, HTML or PDF |
| S2 | Who | **Upload:** anyone who can see an *active* record. **Remove/restore:** same. **Erase:** platform owner only |
| S3 | Physical deletion | Edge Function `continuity-attachment-cleanup` using the Storage API. It is called with a shared secret |
| S4 | Upload path | Edge Function `continuity-attachment-upload`. It checks the file signature on the server. Users have **no** write policy on the bucket |
| S5 | Retention | Same as excerpts: unreadable at once 365 days after closure; the hourly sweep then marks the row `redacted` and queues the file |

If any of these should differ, it is a small change before go-live.

## What changes
### Database (`migrations/080_continuity_attachments.sql`, requires 079)
**The bucket `continuity-attachments`:**
- private;
- `file_size_limit` 16 MiB;
- `allowed_mime_types` is the 13 types above;
- **one** policy on `storage.objects`: `continuity_attachments_read`, `SELECT` for `authenticated`, calling `_continuity_attachment_readable(name)`;
- **no** `INSERT`, `UPDATE` or `DELETE` policy.

The read rule `_continuity_attachment_readable(name)` returns true only when **all** of these hold:
- the attachment is `active`;
- the caller can see the record now (`continuity_can_access`);
- the capability is on;
- retention has not expired.

**The table `continuity_attachments`:**
- **Path:** generated by the server: `<workspace>/<record>/<attachment>`. No user file name or extension is used in it.
- **States:** `pending → active → removed ⇄ active`, then `purged`, `redacted` or `abandoned`, which are final.
- **Protection:** a guard trigger blocks delete and truncate, and rejects any change to the path, size, hash, type or creator, as well as any un-finalising.
- **Deleting a staff profile** sets `created_by` / `removed_by` / `purged_by` to NULL and keeps the row (tested).
- **Conventions:** no grants, the 041/042 conventions, and the verification block aborts on drift.

**RPCs for `authenticated`:**
- `continuity_attachment_begin`: checks access, that the record is active, the capability, the type and size, the 20-file cap (serialised by a record lock) and idempotency.
- `continuity_attachment_commit`: verifies the **stored** object (it exists, its size matches exactly, its MIME matches).
- `continuity_attachment_remove`, `continuity_attachment_restore`, `continuity_attachment_purge`.
- **Count:** 27 `continuity` functions are executable by `authenticated` (21 before).

**Also:**
- **Sweep** `continuity_attachment_sweep()`: pg_cron `continuity-attachment-sweep`, hourly at :23.
- **Service role:** `continuity_attachment_deletion_queue(limit)` is the **only** continuity function `service_role` can execute. It returns paths only (exception documented in the migration).
- **`_continuity_full`** gains `attachments` and `removed_attachments`. Both are empty while the capability is off.
- **Capability marker:** `_continuity_capability_attachments()` makes the capability *installed*. It stays **off**: 078's `attachments_enabled = false` is not touched.

### Edge Functions
**`continuity-attachment-upload`** (logic in `handler.js`, tested in Node):
- verifies the user's JWT;
- calls begin and commit **as the user**;
- reads the body with a hard cap;
- checks the magic bytes against the declared MIME;
- computes sha256;
- uploads with the service role to the generated path, with no upsert.

The service-role key exists only in the function environment.

**`continuity-attachment-cleanup`** (logic in `handler.js`):
- refuses every request unless `X-Cleanup-Secret` equals `CONTINUITY_CLEANUP_SECRET`;
- deletes only paths shaped `<uuid>/<uuid>/<uuid>`, in batches of 100.

### Frontend
- **A «المرفقات» section** on the record page, shown only when `continuity_my_access.capabilities.attachments` is true.
- **Media:**
  - shown through 300 s signed URLs;
  - names are escaped;
  - removed attachments show no media and request no URL;
  - a refused signature shows «المرفق مش متاح دلوقتي».
- **Upload:**
  - browser pre-checks of type, size and signature (advisory only);
  - progress bar and cancel;
  - retry reuses the same idempotency key.
- **Closed record:** view only.
- **Erase:** platform owner, behind a danger dialog.
- **The only non-RPC request in the Continuity UI** is in `assets/js/continuity/continuity-upload.js`: one `POST` of the file to the upload function. A test enforces this.

## Deploy order (each step separately approved)
1. Apply 077, 078 and 079 (earlier PRs), then **080**. Attachments are installed and off, and nothing is uploadable (no write policy, no deployed function).
2. Deploy `continuity-attachment-upload` and `continuity-attachment-cleanup`. Uploads are still impossible while the capability is off: begin returns `feature_not_enabled`.
3. Set `CONTINUITY_CLEANUP_SECRET`, then schedule the cleanup call. One option is a pg_cron job using `pg_net` and a Vault secret; that would be a small follow-up migration, not included here.
4. Deploy the frontend. The section stays hidden while the capability is off.
5. **Decision:** switch on `attachments_enabled` (owner, `continuity_set_policies`), then verify (below).

The daily production-drift job will list 080 and the two functions as "not applied / not deployed" until steps 1–2. This is expected and matches 077–079.

## Rollback
- `migrations/_rollback/080_continuity_attachments.down.sql`:
  - restores `_continuity_full` to its 079 text, byte for byte (tested);
  - drops the read policy, the functions, the table and the cron job.
- It refuses to run while any attachment is pending, active or removed, or any object remains in the bucket, unless `continuity.rollback_discard_data = 'on'` is set.
- **The bucket itself is not dropped.** Storage forbids SQL deletes, and files are deleted only through the Storage API. With no policy left it is closed: no reads, no writes. Empty it with the cleanup function or the dashboard, then delete it there.
- 079's rollback now refuses while 080 is installed (tested).

## Residual risks and limits
- **A signed URL stays valid for up to 300 s** after removal, erase or loss of access. This is the same accepted window as chat and ticket attachments; new URLs are refused immediately.
- **The browser checks are advisory.** The server repeats every check: the function checks size and signature, and the database checks the stored size and MIME.
- **The sha256 is computed by the upload function** and recorded for audit. It is not re-verified by the database, which cannot read object bytes.
- **The upload function reads the file in memory,** at most 16 MiB.
- **The function's CORS allows any origin.** That matches the repo's other functions, and authentication is the bearer token, not cookies.
