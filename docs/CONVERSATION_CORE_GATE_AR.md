**Conversation Core (064 + 067) جاهز يتطبق على staging.** كل الفجوات اللي اتلقت في 064 اتقفلت، وكل إصلاح ليه إثبات «قبل» (على 064) و«بعد» (على 067)، على قاعدة بشكل الإنتاج، باتصالات متزامنة حقيقية.

**الحكم على 064 كما هو:** التصميم سليم في جوهره: الأقفال، والنسخة، والـ fencing. لكنه كان **غير آمن للتطبيق** بسبب 7 عيوب حقيقية: D1، D2، D3، D4، G1، N1، L1. كلهم **مثبتين بسلوكهم الفعلي** في الجزء ① من اختبار البوابة (`PROVEN GAP …`).

### إعادة نظر في التصميم نفسه (بصراحة)

1. **`conv.source` كان بيتسرّب.** الـ GUC المحلي بيفضل مضبوط لآخر المعاملة. للأحداث ده مقبول، لكن مايتعتمدش عليه كإذن. 067 استخدم علم ضيّق اسمه `conv.writer` بيتفتح قبل الإدراج ويتقفل بعده، وبيترجع تلقائيًا لو الـ savepoint فشل.
2. **«الأعلام بتحمي» كانت افتراض في الكود اللي بينادي، مش في القاعدة.** ده كان أكبر عيب تصميمي. 067 نقله للقاعدة: سياسات RESTRICTIVE + محفّز كاتب الخادم الواحد.
3. **نموذج «آخر رسالة بتكسب».** لو جت رسالتين ورا بعض، دور الأولى بيترفض، والـ Orchestrator **لازم** يعيد `decide` على الحالة الأحدث. لو ده ماتعملش، الرسالة الأولى مالهاش رد. ده مش عيب في القاعدة، لكنه **شرط إلزامي** على الـ Orchestrator (§6).
4. **الإرسال at-least-once.** لو الـ lease انتهى ممكن رسالة تتبعت مرتين على تيليجرام (مالوش idempotency key). مقبول وموثّق، ومش هيتحل في القاعدة.
5. **حدث لكل رسالة في `inbox_events`.** بيضاعف الكتابة. مش مشكلة عند 483 رسالة، لكنه محتاج partitioning قبل الملايين.

## 3. الفجوات الأربع: التصميم والإثبات

### D1: حصة التذاكر
**السلوك المطلوب:** رد العميل **عمره ما يختفي** بسبب التذكرة.

**الـ semantics:**
1. قفل الحصة الاستشاري يتاخد **قبل** قفل الجلسة (نفس ترتيب المسار القديم ومحفّز 065).
2. إدراج التذكرة جوه **savepoint** (`begin … exception`):
   - **الحصة خلصت** (`P0001` + hint `ticket_quota_exceeded`/`billing_quota_exceeded`):
     - الرد يتسجّل، ونص 065 نفسه (مكتوب للعميل) يتضاف بعده.
     - مفيش تذكرة، و**مفيش تأكيد كاذب**.
     - المحادثة تفضل مع البوت.
     - يتسجّل حدث `ticket_failed`.
     - النتيجة فيها `ticketError`.
   - **فشل غير متوقع** (أي sqlstate تاني):
     - الرد يتسجّل، ونص ثابت «ماقدرناش نفتح التذكرة…» يتضاف.
     - **تسليم لإنسان** (`ticket_failed`)، لأن حد لازم يشوف التذكرة اللي ماتفتحتش.
     - حدث فيه الـ sqlstate.
   - **فشل عابر** (`40001`، `40P01`، `55P03`، `57014`): مايتمسكش. الدور كله يترجع ويتعاد، مش يتسجّل ناقص.
3. **الرسالة نفسها لو فشلت** ⇒ المعاملة كلها تترجع، **والتذكرة معاها** (T11 بفشل محقون).
4. `p_ticket.confirmation` بتاخد `{ticket_number}`، فالتأكيد بيتكتب **بعد** ما الرقم يبقى حقيقي. SIE مابيقدرش يقول «فتحتلك تذكرة» قبلها.

**الإثبات:** D1، D1b (فشل `23514`)، D1c (تأكيد برقم + محفّز الإيميل اشتغل)، T11، E (تزامن)، L1.

### D2: المرفقات
- `conv_ingest_message(..., p_attachment jsonb)`:
  - بيكتب `attachment`، ومعاه `image_url`/`audio_url` بنفس شكل 054 وردود الدعم.
  - بيعدّي على **حارس 054 نفسه**: المسار لازم يكون في مجلد المرسل، والملف موجود فعلًا في `chat-attachments`.
  - لو مفيش نص بيكتب نص تلقائي **مطابق لـ `autoLabelFor`** في الويدجت.
- **المسار كامل:** رسالة واردة ← بيانات المرفق ← `chat_messages` ← الصندوق (المشرف شايفه عبر RLS بتاعته).
- **الفيديو:** **مش مدعوم في المنتج أصلًا.** قيد 054 بيسمح `image/audio/file` بس، والويدجت بيرفضه. Core بيرفضه بـ `22023` **قبل أي كتابة**. لو عايز فيديو ده قرار منتج: توسيع 054 والويدجت والـ bucket.

**الإثبات:** D2. فيه صورة بتعليق، وصوت من غير نص، وملف، والمشرف شايف التلاتة. ومسار في مجلد غيره ⇒ `42501`، وملف مش مرفوع ⇒ `42501`، وفيديو ⇒ `22023`، وكلهم من غير ما يسيبوا أثر.

### D3: ملكية الإنسان
**الثابت:**
> مالك المحادثة مابيتغيرش إلا عبر `_handoff_set` (`inbox_take_over` / `inbox_return_to_ai` / `sie_request_human` / رد الصندوق / تسليم الوكيل) أو إقفال صريح من موظف أو العميل. **الخمول عمره ما بيغيّر المالك.**

- محادثة Core خاملة وماسكها إنسان ⇒ مابتتقفلش، والرسالة الجديدة بتنضاف لنفس المحادثة (owner=human).
- جلسة قديمة (قبل Core) خاملة وماسكها إنسان ⇒ **بتتبنّى** ومابتتسابش جنب محادثة بوت جديدة.
- **التزامن:**
  - الاستلام الأول ⇒ الوارد بيستنى القفل ويكمّل مع الإنسان.
  - الخمول الأول (محادثة بوت) ⇒ المحادثة تتقفل، والاستلام بعده **يفشل صريح** (060). مفيش حالة في النص.

**الإثبات:** D3، D3b، D3c (اتصالين حقيقيين بالترتيبين).

### D4: مين الكاتب الوحيد؟

**جرد كل كتابات العميل المباشرة النهارده:**

**كتّاب الخادم القدام** (`persist_bot_turn`، `create_ticket_with_message_and_session_update`، مسار تيليجرام القديم): لما العلم يتفتح ⇒ `55000`، **ومن غير تذكرة يتيمة** (المعاملة كلها بتترجع).

**المعمارية:**
- **الكاتب الآلي الوحيد** لأي محادثة علمها مفتوح = `conv_ingest_message` (رسالة العميل) + `conv_commit_turn` (رد البوت). ده **مفروض في القاعدة**.
- **الكاتب البشري الوحيد** = دوال الصندوق (`inbox_send_reply` …). بتعدّي على `_handoff_set`، فبتزوّد النسخة وبتسكت البوت تلقائيًا.
- **العميل:** بيقرا محادثته، وبيرفع ملفات لمجلده، وبيقفل محادثته. **ولا حاجة تانية.**
- **قفل العلم** ⇒ كل الحواجز دي بتتشال تلقائيًا والسلوك القديم بيرجع بالظبط. ده اللي بيخلّي الرجوع ممكن من غير deploy.

**الإثبات:** D4 (الطرح لـ C1 بس، وC2 برا الطرح قديم، والإقفال بس، و100%، والرجوع)، D4-writers.

### فجوات إضافية اتقفلت
- **G1:** `conv_account_active(user)` = نفس `account_is_active()` بس بمعامل. المحظور ⇒ `42501`، والمنتظر ⇒ `42501`، من غير أثر.
- **N1:** `turn:` محجوز. والصف القديم اللي حجز مفتاح قبل 067 بيخلّي الـ commit **يفشل صريح** (`23505`) بدل duplicate صامت.
- **R1:** `conv_claim_delivery(..., p_max_attempts=5)`. بعد الحد الأقصى الرسالة بتبقى `failed` نهائي. ولو العامل وقع في آخر محاولة مسموحة، `failed` بدل `sending` للأبد.
- **F1:** الأعلام بتقبل `true/false` أو `{"enabled":true,"users":[…],"percent":0..100}`. الطرح التدريجي حتمي بالمستخدم (hash ثابت).

## 5. التزامن الحقيقي (A–E)
كل الحالات دي بـ **اتصالات dblink منفصلة**، وكل واحدة بتتأكد إن التاني **وقف فعلًا على قفل** (`pg_stat_activity`) قبل ما الأول يثبّت. يعني مش مجرد تشغيل ورا بعض.

| | الحالة | النتيجة |
|---|---|---|
| A | رسالتين واردتين في نفس اللحظة | التانية استنت، `seq`/نسخة +1، نفس المحادثة |
| B | دور بوت + استلام إنسان (الترتيبين) | الاستلام الأول ⇒ `human_owner` من غير رد ولا تذكرة. الرد الأول ⇒ الاستلام استنى وحدثه بعد الرد |
| C | نفس `turn_key` من اتصالين | رسالة واحدة، والتاني duplicate بنفس `messageId` |
| D | مطالبتين إرسال متزامنتين | مطالبة واحدة |
| E | تذكرة واحدة فاضلة ومحادثتين متزامنتين لنفس الحساب | تذكرة واحدة بس، والتاني ردّه اتسجّل بسبب الحصة |
| + | المسار القديم + Core (L1) | 064: deadlock مثبت. 067: اتسلسلوا والاتنين نجحوا |
| + | استلام ↔ وارد خامل (D3c) | الترتيبين حتميين |

**عيب لقيته في طريقة الاختبار نفسها، واتصلح:** `pg_stat_activity` بيتصوّر مرة واحدة لكل معاملة. لو مفيش `pg_stat_clear_snapshot()`، الفحص التاني في نفس البلوك بيشوف صورة قديمة. ده كان هيخلّي اختبار تزامن ينجح أو يفشل لسبب غلط.

## 6. العقد مع SIE (بدون تعديل SIE الآن)

```
Incoming → conv_ingest_message → [owner=agent?] → SIE.decide(read-only) → Decision
        → conv_commit_turn(expected_version, turn_key) → [delivery_required?] → claim/send/record
```

### `DecideRequest` (اللي الـ Orchestrator بيبعته)
```jsonc
{
  "contractVersion": "1",
  "conversation": { "id": "uuid", "channel": "website|telegram", "stateVersion": 7, "owner": "agent" },
  "customer": { "userId": "uuid", "locale": "ar-EG", "displayName": "…" },
  "messages": [ // آخر N بالترتيب (seq)، من Core نفسه
    { "id": "uuid", "seq": 12, "role": "customer|agent|human|system", "text": "…",
      "attachment": { "kind": "image|audio|file", "mime": "…", "name": "…" }, "at": "ISO" } ],
  "state": { },            // bot_state كما هو — Core مابيفهموش
  "facts": {               // حقائق قرأها الـ Orchestrator (SIE مايكتبش ولا يحسبها)
    "ticketQuota": { "remaining": 3, "unlimited": false },
    "entitlement": { "hasAccess": true, "plan": "free" } },
  "turnKey": "id آخر رسالة عميل"   // = idempotency key
}
```

### `Decision` (اللي `decide()` بيرجّعه)
```jsonc
{
  "contractVersion": "1",
  "decisionId": "uuid",
  "outcome": "reply | clarify | handoff | noop",
  "reply": { "text": "≤ 4000", "parts": [ ], "options": [ { "label": "…", "value": "…" } ] },
  "intent": { "name": "subscription.how_to", "subject": "whatsapp", "aspect": "how_to|price|status|cancel|complaint",
              "confidence": 0.82, "alternatives": [ { "name": "subscription.price", "confidence": 0.11 } ] },
  "state": { },                    // bot_state الجديدة كاملة، أو null = زي ما هي
  "ticket": { "category": "…", "description": "…", "title": "…", "type": "problem|inquiry",
              "priority": "low|medium|high", "confirmation": "… #{ticket_number}" },   // أو null
  "handoff": { "reason": "…" },    // أو null
  "actions": [ ],                  // تلميحات غير مُعدِّلة بس (روابط مقالات…) — Core بيتجاهل المجهول
  "confidence": 0.82,
  "trace": { "engineVersion": "sie@<sha>", "scenarioId": "…", "knowledgeIds": [ ], "latencyMs": 140 }
}
```

### القواعد
1. **`decide()` مابيعملش أي mutation.** الإثبات المطلوب: SIE بيشتغل في الـ decide phase بدور قاعدة **SELECT بس**، وأي كتابة بتفشل. ده **اختبار عقد** لازم يتكتب في مهمة SIE. حتى استهلاك الحصة (`sie_consume_message`) بيعمله الـ Orchestrator **بعد** `committed=true`، مش SIE.
2. **التحويل:**

   | Decision | `conv_commit_turn` |
   |---|---|
   | `reply.text` | `p_reply_text` |
   | `reply.parts` | `p_reply_parts` |
   | `state` | `p_state` |
   | `ticket` | `p_ticket` |
   | `handoff.reason` | `p_handoff_reason` |
   | `"sie@"+engineVersion` | `p_agent_id` |
   | `turnKey` | `p_turn_key` |
   | `channel ≠ website` | `p_delivery_required` |

3. **`trace` و`intent` و`confidence`** بتتكتب في `chat_engine_trace_events` (server-only)، **مش** في `chat_messages.metadata`، لأن العميل بيقرا `metadata` عبر RLS/Realtime.
4. **`version_conflict`** ⇒ الـ Orchestrator **لازم** يعيد `decide` على الحالة الأحدث (بحد أقصى 2 مرات)، وإلا الرسالة الأقدم تفضل من غير رد (§1-3).
5. **`clarify`:** لو `confidence` تحت عتبة، أو الفرق بين أول احتمالين صغير ⇒ سؤال توضيحي باختيارات، مش تخمين. ده اللي بيفرّق «طريقة اشتراك الواتساب» عن «سعر اشتراك الواتساب» (subject=whatsapp، و aspect=how_to ضد price).
6. **مهلة `decide`:** ≤ 8 ثواني. لو اتجاوزت أو فشلت ⇒ الـ Orchestrator بيعمل commit لرد ثابت من الخادم بـ `agent_id='system'`، ومن غير تذكرة.
