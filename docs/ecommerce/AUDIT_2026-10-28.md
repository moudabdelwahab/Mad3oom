## 1. Reusable as-is

- **Organization model** (`companies` + staff + memberships + isolation): a store is a company with a different *kind*.
- **Company account request → admin approval** flow (068) and the "individual or company?" modal (`company-onboarding.js`).
- **Billing** (`request_subscription_purchase`, admin approval, renew/upgrade/expiry cron) and **entitlements** (`plan_features`, `company_has_feature`, overrides).
- **Integrations Hub**: connections, encrypted credentials, OAuth hold-then-complete, webhook inbox/dedupe/retry, worker, health codes, audit, retention, ticket↔record links, manual customer links, ticket context panel, Integrations page in the company dashboard.
- **Owner shell, context gates, step-up, privileged audit**; owner pages framework (`owner-page.js`).
- Notifications table, company tickets/inbox/conversations (102), company reports.

## 2. Missing for Shopify merchants

1. No notion of *store* account kind or store subscription audience.
2. No Shopify connector (OAuth for Shopify differs: per-shop host, HMAC-signed callback, **expiring offline tokens with rotating refresh tokens**).
3. Hub stores only ticket-linked summaries; no product record type, no bounded order sync, no sync-job state ("last successful sync", retry), no lookup/search.
4. No Shopify compliance webhooks (`customers/data_request`, `customers/redact`, `shop/redact`) — **mandatory** for a public app.
5. No store support categories, no order-request tracking (return/exchange/cancel/refund inquiry), no store dashboard pages.
6. Owner has no cross-store diagnostics, no store-plan management, no safe test-store path.

## 3. Database changes (additive, versioned)

- **118** `companies.account_kind` (`company`|`ecommerce_store`, default `company`), request `account_kind` + store hints; `subscription_plans.audience`; plan `store` seeded **inactive with NULL prices** (no invented pricing); feature flags `shopify_integration`, `store_support`; audience trigger on purchases; `my_account_type()`.
- **119** Shopify provider (disabled) and `product` record type in the hub; `ihub_connections.granted_scopes/external_account_gid/last_sync_*`; `ihub_sync_jobs`; token-refresh lease; queued events; compliance requests; `store_support_categories`, `store_ticket_meta`, `store_order_requests` (+ events); store summary/report RPCs; owner diagnostics/test-store RPCs.

## 4. Authentication & authorization changes

- Shopify actions keep the hub rule: every Edge action starts with a user-scoped RPC under the caller's JWT; the server derives the company from `auth.uid()`; secrets only through `ihub_svc_*` (service_role).
- Shopify connect additionally requires `account_kind = 'ecommerce_store'` and `shopify_integration`.
- Store order data visible to company staff with role ≥ the connection's `min_view_role` (default admin); never to customers or other companies.
- Owner gets **read-only metadata** diagnostics (no tokens, no customer/order data) behind `owner_capability('owner_only')`; writes (store plan, test-store) need `owner_critical_ok()` (step-up) and are written to `privileged_audit`. No Admin capability is granted to the Owner.

## 5. Subscription & billing changes

- Account type (individual/company/store) is separate from subscription status (`whatsapp_subscriptions.status`).
- Store plans use the existing request → approval flow. A plan with `audience = 'ecommerce_store'` can only be requested by the owner of a store organization (trigger, also for direct API calls).
- The seeded `store` plan cannot be bought until the Owner sets prices **and** activates it (`owner_configure_store_plan`, step-up). Pricing, the plan's feature bundle and ticket quota are flagged as **product-owner decisions**.

## 6. Shopify integration requirements (verified on shopify.dev)

| Topic | Requirement |
|---|---|
| Distribution | Multi-merchant SaaS → **public app** (unlisted at first, App Store listing later). Custom distribution is single-merchant/Plus-org only and does not scale. A development-store install proves nothing about review. |
| Auth | Non-embedded app → **authorization code grant**. Callback must verify `hmac` (hex HMAC-SHA256 of the sorted query without `hmac`, client secret), `state`, and `shop` against `^[a-zA-Z0-9][a-zA-Z0-9\-]*\.myshopify\.com$` (anchored). Token exchange `POST https://{shop}/admin/oauth/access_token`, form-encoded, with `expiring=1`. |
| Tokens | "New public apps must use expiring offline access tokens": access ~1 h, refresh 90 days, **refresh token rotates** → single refresher with a lease. 401 on refresh → reauthorize. |
| Scopes | Verify granted `scope` (merchant can change it). Mad3oom requests `read_orders,read_customers,read_products` only. Orders older than 60 days need `read_all_orders` (not requested). |
| Protected customer data | Name/email/phone/address fields need **Level 2 approval**; unapproved fields return `null` + an `errors` entry with HTTP 200. Dev stores work without review. Level 1/2 obligations (minimization, retention, encryption, access logs, incident policy) apply. |
| Webhooks | App-specific subscriptions in `shopify.app.toml` (recommended; not deleted on failures; the only way to subscribe compliance topics). Verify `X-Shopify-Hmac-Sha256` (base64, raw body, client secret); 401 on mismatch; respond 2xx within 5 s; 8 retries over 4 h; dedupe by `X-Shopify-Webhook-Id`; no ordering guarantee → order by payload `updated_at`; run reconciliation. |
| Rate limits | GraphQL cost bucket (`extensions.cost.throttleStatus`), max 1,000 points/query, ~1 s backoff. |

## 8. Security risks & tenant-isolation issues found

| # | Risk | Disposition |
|---|---|---|
| S1 | Shopify OAuth account-linking CSRF (attacker sends a victim an install link) | Reuse hub hold-then-complete (state + tab binding + completion code + initiating admin) and bind the expected shop to the state |
| S2 | Malicious `shop` host → token exchange to attacker host (SSRF / code theft) | Anchored myshopify regex on the server; host never taken from the browser unvalidated |
| S3 | Refresh-token race (rotation) | DB lease on refresh; single writer |
| S4 | Duplicate/out-of-order webhooks | Dedupe on webhook id; apply only if `updated_at` not older (existing `apply_record` rule) |
| S5 | Protected customer data over-collection | Allowlisted summaries ≤ 4 KB; masked e-mail; no street address; no phone stored; 30-day cache retention; compliance redaction |
| S6 | Owner diagnostics becoming a cross-tenant data window | Metadata only (counts, codes, timestamps); no customer, order, token or secret fields |
| S7 | Pre-existing: `ticket_in_my_scope` lets any account with followers see followers' tickets (documented in 088 review) | Unchanged; Shopify context additionally requires company + staff role |
| S8 | Pre-existing: `meta-webhook`/`resend-inbound-webhook` fail open when secrets unset | Out of scope; Shopify endpoints fail **closed** (503) |
